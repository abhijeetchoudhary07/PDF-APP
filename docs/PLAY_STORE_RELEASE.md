# Google Play release guide

What is ready in this repository, and what still has to happen outside it before
Indian Form Helper can be uploaded to the Play Console.

---

## 1. Identity and configuration

`capacitor.config.ts` is set for production:

| Key | Value |
| --- | --- |
| `appId` | `com.pdfhelper.indianformhelper` |
| `appName` | `Indian Form Helper` |
| `webDir` | `www` |

> **The `appId` is permanent.** Google Play binds it to the listing on the first
> upload and it can never be changed afterwards — a different package name is a
> different app, with a different install base and a different review history.
> Change it now if `com.pdfhelper.indianformhelper` is not the identity you want.

Also configured there: `allowMixedContent: false` and
`webContentsDebuggingEnabled: false` (both are flagged by Play's pre-launch
report when left on), a `SplashScreen` block, `StatusBar` with
`overlaysWebView: true` for edge-to-edge, and `Keyboard` with `resize: 'none'`
so the OS does not double-scroll a focused field.

---

## 2. Adding the Android platform

The repository has no `android/` directory yet. It is generated, not authored:

```bash
npm install --save @capacitor/android @capacitor/splash-screen
npx cap add android
npm run build
npx cap sync android
```

`@capacitor/splash-screen` is what makes the `SplashScreen` config block take
effect; without it the keys are inert and Android falls back to its own
launch theme.

## 4. Signing and the release build

```bash
keytool -genkey -v -keystore indian-form-helper.keystore \
  -alias indianformhelper -keyalg RSA -keysize 2048 -validity 10000
```

Keep the keystore and its passwords out of the repository. Configure
`android/app/build.gradle` with a `signingConfigs.release` block that reads them
from `gradle.properties` or the environment, then:

```bash
npm run build && npx cap sync android
cd android && ./gradlew bundleRelease
```

The `.aab` lands in `android/app/build/outputs/bundle/release/`.

Set `versionCode` and `versionName` in `android/app/build.gradle` before every
upload — Play rejects a duplicate `versionCode`.

## 5. Data Safety form

The answers are written out in full on the Privacy Policy page, section 8
(`/features/privacy-policy#data-safety`). Enter the same answers in the Play
Console so the label and the policy agree:

- **Files and documents** — not collected, not shared. All processing is on device.
- **Photos** — not collected, not shared.
- **Email address, display name** — collected only if the user creates an
  account; not shared; used for account management and entitlement sync.
- **Purchase history** — collected for subscription verification and restore;
  not shared beyond Google Play / RevenueCat.
- **Device or advertising identifiers** — **not collected, not shared.** The
  app ships no advertising SDK, and `com.google.android.gms.permission.AD_ID`
  is not in the manifest. Verify before submitting with:
  `aapt2 dump permissions <aab-or-apk> | grep AD_ID` — it must print nothing.
- **App activity and crash logs** — **not collected.** There is no analytics
  provider wired up; `AnalyticsService` records events locally and sends
  nothing.
- **Data in transit is encrypted** — yes (HTTPS on the optional account endpoints).
- **Users can request data deletion** — yes, from the Account screen, which
  calls `DELETE /api/v1/pdf-app/auth/me`. Deletion is real: every `pdf_` table
  keyed on the user cascades, and audit rows keep the admin action while
  dropping the identity.

> Earlier revisions of this section told you to declare advertising IDs shared
> with AdMob and app activity shared with Firebase. Both plugins have since
> been removed -- they were never configured and only added permissions the app
> made no use of. Declaring collection that does not happen is its own policy
> problem, so the rows above are the ones that match the binary.

## 6. Government-apps policy

The app is named and themed around Indian exam and job forms, which Play treats
as a government claim unless it is disclaimed. The notice renders in three
places from one component (`app-gov-disclaimer`) and one translation key
(`footer.govDisclaimer`, present in all five locales):

- the footer of every page that renders `app-footer`;
- `/features/settings`, directly under the navigation tabs;
- `/features/about-engine`, closing the page.

A fourth, longer version is in the Terms of Use. If the wording is changed, change
`footer.govDisclaimer` in `src/app/core/i18n/translations/*.ts` — nothing else
hard-codes it.

## 7. Payments — manual UPI, not Play Billing

Premium is sold by **manual UPI transfer**: the person pays in their own bank
app, submits the UTR/reference in the paywall, and an admin confirms it. There
is no Google Play Billing integration in the shipped flow.

### ⚠️ Read this before submitting to Google Play

Google Play's Payments policy requires **Google Play Billing** for digital
content and features unlocked inside the app. An in-app UPI flow that unlocks
premium is the single most common cause of app suspension under that policy.

This is a product decision, not a technical one, and it was made deliberately.
The ways it can be made compliant, in rough order of effort:

1. **Sell outside the app.** Move the pay panel to a website and let the app
   only *restore* an entitlement the account already has. Play permits an app to
   recognise a purchase made elsewhere; it does not permit collecting the
   payment in-app.
2. **Enrol in Google's alternative billing** (User Choice Billing), available in
   India, and pay the reduced service fee.
3. **Ship outside Play** — direct APK, or another store.
4. **Add Play Billing alongside**, and show the UPI flow only where Play Billing
   is unavailable.

The code is arranged so option 1 or 4 is a small change: the paywall reads
`PdfPaymentSettings.isActive` to decide whether to show the pay panel at all.

### How the flow works

| Step | Where |
| --- | --- |
| Paywall shows plans and a "Pay ₹X" CTA | `src/app/features/premium/premium.page.*` |
| Panel shows UPI id, a QR generated on device from the UPI intent, and optional bank details | same |
| Person pays in their own UPI app | — |
| Reference submitted | `POST /api/v1/pdf-app/subscription/manual-payment` |
| Claim recorded as `pending` — **grants nothing** | `pdf_manual_payment_requests` |
| Admin approves | `POST /api/v1/pdf-app/admin/manual-payments/:id/approve` |
| Entitlement granted via the normal path | `grantPremium(..., platform: 'manual_admin')` |
| App unlocks on resume, or on "Check status" | `MonetizationService.refreshFromServer()` |

The backend lives in the **`linkedin AUTO`** repository alongside the rest of the
PDF App server:

```
migrations/024_pdf_app_manual_payments.sql          pdf_payment_settings, pdf_manual_payment_requests
server/pdf-app/repositories/pdf-manual-payments.ts  claims and payee settings
api/v1/pdf-app/subscription/payment-settings.ts     GET  payee details (public)
api/v1/pdf-app/subscription/manual-payment.ts       GET  my claims / POST submit
api/v1/pdf-app/admin/manual-payments/               GET  queue, POST approve|reject
tests/pdf-manual-payments.regression.test.ts        18 tests
```

### Safety properties worth keeping

- **A claim is never an entitlement.** Only `grantPremium` grants, and it is
  only reachable from the admin route.
- **The amount comes from the plan row**, never the request body — otherwise
  anyone could claim Lifetime for ₹1.
- **`utr_number` is unique**, so one transfer cannot be claimed twice, including
  from a second account.
- **One pending claim per account** (partial unique index), so an impatient
  double-tap cannot fill the review queue.
- **Approval is guarded by `where status = 'pending'`**, so two admins working
  the queue at once cannot both grant.

### Configuring the payee

Edit the single row in `pdf_payment_settings`:

```sql
update pdf_payment_settings
   set upi_id = 'yourhandle@okicici',
       upi_name = 'Your Registered Name',
       instructions = '...',
       review_hours = 24,
       is_active = true
 where id = 'default';
```

Setting `is_active = false` turns the pay panel off and shows an "unavailable"
notice instead — useful while switching payment rails.

### RevenueCat

`src/app/core/config/store.config.ts` still holds placeholder RevenueCat keys
and `MonetizationService` still refuses to configure with them. That path is
dormant, not deleted: filling in real keys and Play Console products is what
option 4 above would need.

## 8. Free tier limits

A free account may produce **5 completed outputs per day**, reset at local
midnight. Premium is unlimited.

- Service: `src/app/core/services/usage-quota.service.ts`
- Gate and counter: `StorageService.saveFile` — the single point every tool's
  output passes through, so it cannot be bypassed from another screen, and work
  that fails never costs an operation.
- Grouping: pass an `operationId` to `saveFile` when one run writes several
  files (`batch`, `batch-pdf`, `pdf-ocr`). Left out, it is derived from the file
  so save-then-share of the same result counts once.
- Shown before it runs out: desktop header chip, mobile drawer, home hero pill.

The counter is stored on the device (`IFH_DAILY_USAGE_V1`), not on the server,
so the tools keep working offline. That means clearing app data resets it —
accepted deliberately rather than breaking the offline promise. **Do not** wire
`UsageQuotaService.reset()` to the in-app "Clear history" or "Factory reset"
controls.

### Pricing

Prices live in `pdf_plans` (server, source of truth, changed by a migration —
see `025_pdf_app_pricing_update.sql`) and are mirrored in `OFFLINE_PLANS` in
`premium.page.ts` as the bundled fallback for when the server is unreachable.
Change both together. Current: ₹49/month, ₹365/year, ₹999 lifetime.

## 9. Verifying a build

```bash
npm run build            # production build, must be error-free
npm run test:unit        # vitest run --dir src
npm run test:e2e         # Playwright against `ng serve`
npm run test:e2e:prod    # Playwright against the production bundle in www/
```

### Which Playwright target to use

`npm run test:e2e` runs against the dev server. `npm run test:e2e:prod` builds
once and serves `www/` over a dependency-free static server
(`tools/serve-www.mjs`). Prefer the second one, and use it in CI.

The reason is not speed, though it is faster: `ng serve` compiles each lazy
route the first time something requests it, so with the suite running in
parallel those compiles queue behind each other and tests fail on navigation
timeouts that have nothing to do with the app — the same tests pass one at a
time. A pre-built bundle removes the variable, and it is the artefact that
actually ships.

One consequence: the production bundle is wired to the **live** accounts
backend by `environment.prod.ts`, so the suites that register accounts and ask
an admin endpoint to grant premium (`e2e/account/`, and the `@journey` tests in
`e2e/release/user-journey.spec.ts`) skip under `test:e2e:prod` rather than
create real accounts on the production server. Run those against the dev target
with the local API up — see the backend section below.

### What `e2e/release/` covers

| Spec | Covers |
| --- | --- |
| `language-selector.spec.ts` | The navbar language menu: that it opens, that every option is on screen rather than clipped, that a choice translates the app and survives a reload and a route change, and that the header fits at nine widths in the longest-labelled locale |
| `user-journey.spec.ts` | Sign up → use a tool → sign out → sign back in as one arc, plus client-side email and password validation (nothing is sent to the server when it is wrong) |
| `ui-interactions.spec.ts` | The Tools mega menu, the global search modal, the mobile drawer — geometry and hit-testing, not CSS classes |
| `file-handling.spec.ts` | Upload acceptance and refusal for images and PDFs (unsupported type, empty, corrupt, oversized), multi-file input, output, and free-vs-premium tier behaviour |
| `free-tier-quota.spec.ts` | The daily allowance, its reset, and where it is shown |
| `premium-compliance.spec.ts` | The paywall, UPI panel, pending and rejected claims, and payment disclosures |
| `mobile-navbar.spec.ts` | Touch targets and horizontal overflow at 360/390/412/430 |
| `feature-navigation.spec.ts` | Every tool route loads with a console-error gate |
| `not-found.spec.ts` | The 404 route |
| `store-policy.spec.ts` | Privacy policy, terms, and the government-apps disclaimer |

Two tests — `TIER-004` and `UI-002` — call `test.slow()`. They each walk more
than a dozen routes in one test, which is real work rather than a hang; against
the production bundle they finish inside the default timeout anyway.
